`verify_owner_observation(connection, principal)` vérifie dans la vraie table `users` un objet ayant ID entier positif, rôle `ADMIN` ou `DENTISTE`, actif, approval `approved`, `employer_id IS NULL`, et vérifie la concordance avec l'enregistrement relu dans la base. **Attention** : un simple objet Python ressemblant à un utilisateur authentifié n'est PAS une preuve de provenance de la dépendance API, de session Windows ou de login. `evaluate_tenant_snapshot_read_only(connection, principal, expected_owners=...)` vérifie que `alembic_version == neo000000031`, que les deux propriétaires synthétiques attendus existent dans les scopes, et cherche en lecture seule sur les **vrais modèles** six catégories d'anomalies : propriétaire des patients, rendez-vous/patient, rendez-vous/ressource, acte/praticien, paiement/acte, document/auteur. Les résultats sont agrégés : jamais de données de patient dans l'exception. `PRAGMA foreign_key_check` est exigé pour SQLite. Un résultat positif indique seulement une **observation partielle** ; il retourne toujours `clinical_import_permitted=False` et `clinical_restore_permitted=False`. Les centaines d'autres relations Cabinet et la justification juridique, les identités externes, les registres auditables et médias sont hors preuve.

## Publication exclusive du LAB, pas une restauration d'exploitation

`fake_lab_publish_no_replace(root,staged,target,expected_sha256)` ne peut agir que sous `LOT05G_SYNTHETIC_ONLY=1`, une racine temporaire au préfixe fixe `lot05e_fake_sqlcipher_*` et des chemins **exacts** dans son sous-dossier de test (staging `.lot05g_stage_*.db`, destination `restored_fake.db`). Il refuse liens symboliques observés, dossiers réorientés, destination déjà occupée, hash invalidé. Il publie via `os.link(staged,target,follow_symlinks=False)` ; si collision EEXIST ou liens durs indisponibles, il **échoue**, sans `os.replace`, copie fallback ni purge de la destination. La collision peut être injectée juste après le calcul du hash dans le test adversarial.

Le laboratoire **utilise vraiment** l'opérateur `python -m alembic upgrade head` (dans la fixture synthétique 05.7-E), le driver SQLCipher natif, les vraies classes ORM, `BackupService.backup_active_database()`, `BackupService.restore_backup(verify_sqlcipher=True)` exclusivement en staging fictif, les contrôles read-only, puis la publication. La validation du contenu avant publication est explicite dans le test (Alembic, lignes réelles mais fictives, SQLCipher). Ce module n'exécute **pas** de restauration clinique. Ne pas copier tel quel le code de hardlink dans un worker Cabinet.

### Réserves sécurité/fiabilité OUVERTES

- **Risque runtime réel, non modifié** : `GuidedRestoreWorker._apply_database` supprime le WAL/SHM de la cible et utilise `os.replace(temp,target)`; `BackupService.restore_backup` utilise `os.replace` pour sa cible. L'applicabilité d'un hardlink à un fichier de Cabinet en exploitation est **non prouvée et ne suffit pas**.
- **Risque identité réel** : `GuidedRestoreService._assert_owner(job, None)` retourne sans vérifier le propriétaire (permet un appel interne sans owner) ; l'identité doit devenir **obligatoire et attestée** à chaque passage de frontière (API, job, worker/SCM). L'observation ORM ne remplace jamais ce contrôle.
- **Windows NTFS** : contrôles `Path.is_symlink` et `Path.resolve` observés, mais aucun handle de répertoire sécurisé ni DACL/ownership/SID, jonction/reparse/hardlink attaquant, TOCTOU parent/race inter-processus ou usurpation du chemin n'est démontré. `os.link` échoue volontairement si la fonctionnalité manque et ne prouve aucune durabilité fsync sur dossier.
- **Sauvegarde complète** : pas de protocole atomique multi-fichiers pour SQLCipher/WAL/SHM, coffre des clés, licence, médias, images, consentement source, migration/destruction historique, tests de charge, reprise secteur, RPO/RTO ou preuves post-restauration Windows Service/SCM. Pas d'import patient ni de restauration autorisée. Voir `techdoubt.md`.
- **Évaluation propriétaire** : les `expected_owners` du laboratoire sont des ID créés sur place. En réel, l'autorité ne peut venir d'un ID fourni par l'utilisateur ni d'une simple variable de contexte ; vérification indépendante indispensable.
