## Problème résolu, sans invention
En 05.2-B1, le manifest cible doit être importé en JSON depuis une source technique non certifiée. 05.2-B2a introduit une **fonction pure de prévisualisation** lisant uniquement `sqlalchemy.MetaData` des déclarations ORM afin de proposer tables et colonnes existant **dans le code du modèle**. Elle ne fait AUCUNE connexion, reflection de base de données, changement Alembic ou lecture patient. Elle n'authentifie PAS l'identité utilisateur et n'est enregistrée sous aucune route.

Le service `backend/services/legacy_sql_target_manifest_v15.py` exige une liste de tables cibles explicitement choisie, refuse les inconnues, doublons/collision de casse, noms dangereux, tables d'identité/credential telles que `users`, nombre ou taille exorbitants, retire des champs de secrets/privileges. Chaque exclusion est comptabilisée ; les tables sans aucun champ sûr sont refusées, non supprimées silencieusement. Fournit un hash déterministe du schéma ORM déclaré, un manifest JSON à 2 clés pour l'UI locale de B1 et une `TargetSnapshot` correspondant au moteur 05.2-A.

**Distinction absolue** : `schema_revision = "orm-declared:" + declared_revision`. Cette valeur est le **label du schéma attendu dans le code**, pas l'Alembic réellement installé sur le poste. Tous les drapeaux `physical_schema_verified=false`, `tenant_verified=false`, `admin_approved=false`, `dry_run_completed=false`, `import_permitted=false`. Le hash n'est PAS une signature d'admin ni une preuve de tenant ; aucun profil ne peut être validé/importé sur sa seule base.

## Isolation explicite et matrice Python
L'import de `backend` initialise des services globaux indépendants de 05.2 : l'adaptateur n'importe donc **aucun package backend** à son chargement. Le pont vers le dataclass `TargetSnapshot` du sous-lot 05.2-A utilise l'injection des constructeurs typés ; la CI charge ce module par chemin de fichier, sans initialiser `backend/__init__.py`. Pour inspecter les vraies classes déclaratives des modèles, les tests créent seulement le namespace Python `backend` et importent les déclarations de modèles sans `backend.database`. La constante `DECLARED_EXPECTED_ALEMBIC_HEAD` est comparée par AST à la source `backend/core/schema_runtime.py` : toute divergence casse CI, mais ne constitue PAS un contrôle de la DB réelle.

Le projet épingle SQLAlchemy==2.0.28. Sous Python 3.13, cette version échoue à l'import sur GitHub Actions ([run d'exploration #38322773261](https://github.com/hraaaaf/Digital_crown/actions/runs/38322773261)), indépendamment du code 05.2. La matrice ciblée B2a suit donc Python 3.11 et 3.12 ; **Python 3.13 HORS SCOPE/non certifié** jusqu'à évolution coordonnée du socle ORM. Le run 3.12 initial déclenchait la chaîne d'initialisation du package `backend` (Pydantic manquant dans le job minimal) ; l'isolement source-only a été ajouté avant nouvelle certification.

**Portée exacte des tests** : Python 3.11 = 25 tests ORM B2a et 25 tests Mapping 05.2-A ; Python 3.12 = ces 50 tests plus les 28 tests inspecteur 05.1. Le test `Path.is_junction` du sous-lot 05.1 ne peut pas fonctionner sous Python 3.11, et la CI ne le fait pas passer silencieusement : la suite 05.1 complète est exécutée sur Python 3.12 seulement (ancienne preuve 05.1 existe aussi sous Python 3.13). [Run #38323047241](https://github.com/hraaaaf/Digital_crown/actions/runs/38323047241) documente l'échec exploratoire 3.11 sur l'attente incorrecte de tous les tests exécutés sans skip ; aucun produit runtime n'a été modifié.
