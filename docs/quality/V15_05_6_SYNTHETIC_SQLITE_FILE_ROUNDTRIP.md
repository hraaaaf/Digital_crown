# LOT05.6 — Parcours de fichier SQLite de démonstration (PAS de données cliniques)

PR empilée sur #872. Deux endpoints propriétaires JWT/Workstation/permission + owner : GET `/api/migration/synthetic-fixture` télécharge une vraie base SQLite de **100 faux patients et 200 faux rendez-vous** ; POST `/api/migration/synthetic-file-dryrun` accepte des octets SQLite `application/vnd.sqlite3`, max 512 KiB, en flux borné. La vérification n'accepte **QUE la copie octet-pour-octet du fichier fictif canonique généré par le serveur** — aucun SQLite clinique, SQL fournisseur, CSV, patient réel, export ancien logiciel, fichier modifié ni extension arbitraire.

Dans le navigateur, l'utilisateur doit d'abord télécharger cette copie fictive. Une empreinte SHA256 est calculée localement par WebCrypto et le fichier choisi est comparé avant toute transmission. Sans WebCrypto ou en cas de SHA différente, **aucun octet sélectionné n'est envoyé**. Le serveur revérifie indépendamment l'empreinte à partir du générateur officiel et refuse toute autre base. La lecture se fait par `sqlite3.deserialize` en mémoire, `PRAGMA query_only`, après comparaison cryptographique. Les lignes fictives sont effectivement lues et les valeurs intégralement comparées aux valeurs canoniques ; une autre base portant un marqueur synthétique est REFUSÉE.

La simulation construit séparément 4 tables depuis les vrais modèles ORM déclarés sur `sqlite+pysqlite:///:memory:`, contrôle 100 patients, 200 rendez-vous, leurs 200 liens, les propriétaires et FK ; `rollback` vérifié : 0 patient, 0 RDV, 0 compte de simulation conservé. Aucun octet source déposé sur disque, aucune DB cabinet lue/écrite, aucun modèle ou table métier migré, aucune donnée clinique renvoyée dans le JSON.

**Aucune route d'import réel**. Le Mapping Studio historique conserve les inventaires de schéma et les décisions localement et son bouton Importer reste bloqué. L'application Pocket `/mobile` n'a pas d'écran Migration. Les tests API avec vraie session JWT/Workstation, migrations Alembic réelles, SQLCipher/PG, fichiers fournisseurs hétérogènes, profil signé, backup/restore cabinet, autres données cliniques et approbation UI humaine restent **BLOCKERS**. Ne pas merger ni déployer. Le succès d'un scénario construit par le même serveur n'établit PAS une migration réelle.
