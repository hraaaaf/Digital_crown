# LOT05.4 — First 100/200 row-level SQLite E2E, STRICTLY SYNTHETIC

This is the first large end-to-end **data-value import demonstration**, NOT a clinic migration feature, route, service, Alembic upgrade or permission gate. Draft PR stacked on [#867](https://github.com/hraaaaf/Digital_crown/pull/867), with **no runtime changes**.

## Real operations in the sandbox

1. Create and close a real SQLite source file **inside TemporaryDirectory** containing 100 wholly fictitious `legacy_patients` records and 200 wholly fictitious `legacy_appointments` records. Include `password_hash` and `legacy_notes` as deliberately forbidden fake source columns.
2. Call the **existing** 05.1 `inspect_staged_copy` (staged/offline/SQLite/immutable cold DB) to fingerprint/inventory the physical source. Build and revalidate explicit 05.2-A mapping against **actual declared patient/appointment ORM column names**; keep `admin_approved=false` and `import_permitted=false`.
3. Reopen only the generated source **read-only + immutable + query_only**. Execute only constant allowlisted SQL SELECT statements for patient/appointment **non-secret** columns; never read source credentials or notes, never execute source-provided SQL. Verify SHA before/after, counts, identities, dates, statuses, relationship keys and synthetic markers; fail-closed.
4. Build a **new SQLite TARGET ON DISK inside the same disposable temporary directory**, using the four *real ORM SQLAlchemy declarations* for `users, agenda_resources, patients, appointments` and a separate, conspicuously test-only `synthetic_import_journal` table. That target contains fake users 777/778 and one preexisting fake patient id=900.
5. Transform rows, allocate NEW patient IDs and remap every source patient key to its target patient ID, check ownership against the actually inserted row before each RDV, and write one atomic transaction. Validate every normalized patient tuple and EVERY transformed RDV tuple, not just counts or non-null foreign keys. Physical SQLite FK check, zero orphans, zero cabinet mismatches, 100 newly added patients, 200 newly added RDVs.
6. Produce **two explicitly separate modes**: `dry_run` rolls back all 100/200 candidate inserts, leaving just the original fake patient. A sandbox-only commit persists to the **temporary target** so the result can be independently reopened and backed up. Exact same batch/file replay is NOOP; changed source hash or an unreviewed second batch is refused. Inject a failure after the 73rd patient and prove database state is entirely unchanged.
7. Use SQLite Backup API to snapshot the **synthetic** target into a different temporary file, restore to a third temporary file and compare logical checksums, row counts and both integrity/foreign-key checks. Prove no real cabinet DB, production config/credential, external engine or live patient was ever used.

**Expected**: actual fake source: 100 patients + 200 RDVs. Temporary ORM target after sandbox commit: 101 patients (100 new + 1 fake existing), 200 RDVs, 1 test-only journal row; all 200 correctly linked. After sandbox dry-run: target unchanged with 1 fake patient, 0 appointments, 0 journal row. Restored target parity exact.

## Security & proof caveats

- `backend/tests/test_legacy_sql_sqlite_e2e_100x200_v15.py` is **test-only**, not in `backend/services` or any router/UI; unlike a real product API it has no authenticated staff session. `principal_owner=777` is a **hard-coded fake**, not a user ID retrieved from a real principal.
- The 4-table physical target is built with `create_all`, NOT a complete Alembic-migrated Digital Crown schema; a literal `alembic_version` is not certified; clinical encounter history, funds, images, document metadata and files are excluded.
- This is vanilla SQLite, NOT SQLCipher or PostgreSQL, and the backup covers ONLY fake table rows in this target, not media/assets/auth state.
- `synthetic_import_journal` is *not a production model*; collision/replay logic is a prototype, not concurrency-safe/idempotent under actual imports.
- One known model gap remains: separate FKs do not enforce equality of patient/appointment tenant at DB level, so an explicit server authenticated authorization guard is essential on the eventual real path.
- No staff UI approval and no mobile migration feature tested. A successful CI run does NOT mean this is installable, human validated, merge-ready or ready for real files.
