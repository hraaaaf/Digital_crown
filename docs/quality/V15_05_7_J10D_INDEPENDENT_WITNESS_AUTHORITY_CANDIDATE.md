Scope: LOT05 / 05.7-J10D ONLY. This is a non-activating candidate ADR, **not** an enrollment, integration, cloud deployment, proof of security, clinical restore, vendor approval, or product GO.

## 1. Problem and safety invariant

Observed in exact Windows/Linux CI [run #39415506252](https://github.com/hraaaaf/Digital_crown/actions/runs/39415506252): rollback of the entire locally stored fake SQLite witness reissues previously issued checkpoint 1, although an Ed25519 test signature verifies. The consumer nevertheless returns DENY. A process boundary, local NTFS file identity, DPAPI encryption, TPM key only, signed receipt generated by CI, or separate same-host SQLite DB cannot independently prevent privileged full-state rollback.

**Invariant J10D-WITNESS-01:** A previously durably acknowledged witness operation may never be silently reissued with the same authoritative per-installation sequence, even after full Windows volume/VM/ledger rollback. If witness consistency or independence is in doubt, deny and require controlled reconciliation; never auto-enroll, reset, decrement, trust a client checkpoint floor, or allow clinical restore.

## 2. Candidate architectural choice — RECOMMENDED, NOT APPROVED

**Preferred engineering candidate, subject to explicit owner and legal gates:**
- Independent, separately administered off-host recovery witness, invoked only for exceptional recovery authorization; normal offline clinic usage remains local-first. The witness is not a general patient-data backend.
- AWS KMS asymmetric `ECC_NIST_EDWARDS25519`, `KeyUsage=SIGN_VERIFY`, algorithm `ED25519_SHA_512` with `MessageType=RAW` for production receipts. KMS-managed, non-exported private key; tightly limited signing role. Distinct publisher/Authenticode code-signing chain **still required**. Production domain separator/key identifiers/trust-pinning and key rollover must be specified and reviewed; never relabel the `FAKE` specimen as trusted.
- Separate server-side transactional PostgreSQL state per randomly assigned installation ID, backed by independently administered immutable append-only checkpoint evidence (candidate: S3 Object Lock **COMPLIANCE** mode, independent security account/principal, pinned object-version audit). A PostgreSQL database **alone** is insufficient if its backups/snapshots can be rolled back.
- Minimal receipt fields: schema+domain, pseudonymous installation/enrollment ID, one-time server-bound challenge and client request idempotency ID, pinned publisher signer+consumer binary identities, 24-hex ledger ID as *context only*, committed checkpoint sequence, issued/expiry bounds, key id/algorithm, and explicit **DENY-ONLY during J10D**. No patient identifiers, clinical files, JWT secrets, SQLCipher keys, or patient media over the wire.
- Authenticate and authorize *both* device/enrollment and privileged human recovery request. TLS peer/server authentication and explicit revocation; local Administrator credentials or machine identity alone must not confer restoration authority.

**Why AWS candidate, not automatic vendor selection:** Current AWS KMS official API supports Ed25519 with raw-message semantics; S3 Object Lock COMPLIANCE retains protected object *versions*. GCP KMS supports EC_SIGN_ED25519 but protection-level and key custody requirements need separate evaluation. Microsoft Azure Key Vault documented key types do not currently show Ed25519 as a direct drop-in. No provider has been purchased, provisioned, evaluated operationally or legally accepted.

## 3. Atomicity and state-rollback contract — DESIGN, NOT EXECUTED

The off-host authority must serially compare against an authoritative server-maintained counter; request-supplied floor and local clock are untrusted. Enforce unique (installation, challenge) and (installation, idempotency ID), and at most one issuer advance per committed operation. Never return a usable receipt before both durable authoritative state and separately checkable immutable checkpoint evidence have been established.

The design must define and fault-test ordering across PostgreSQL transaction, KMS signing, immutable journal recording, and network acknowledgement. These are **not** one distributed ACID transaction. If a journal write succeeds but DB COMMIT fails, advance/reconciliation may consume a sequence without authorizing an operation; gaps are safer than reuse. If DB commits but journal evidence is missing or unverifiable, startup and issuing must DENY until independently reconciled. If the response is lost after durability, a retry may return the *identical stored receipt* only on authenticated same-request idempotency, never issue a fresh checkpoint from a stale floor. A replay with a new challenge from restored local state is denied.

On server restore, compute and verify high-water state from independently retained immutable **object versions**, not an untrusted current object-key view. Object Lock protects versions but allows new versions and delete markers; a naive `GET` of the latest key can lie by omission. Store immutable sequence-chain commitments / checkpoint hashes with version IDs and verify completeness, retention and continuity. If the immutable trail is missing, inconsistent, has gaps not explainable by auditable aborted operations, or its identity chain cannot be authenticated: fail closed. Do not assume that a WORM bucket by itself implements a monotonic counter.

Threat boundary: local Windows Administrator/SYSTEM and compromised local backups must not administer the authority, its signer IAM role, authoritative DB, WORM ledger or root pin distribution. Real off-host compromise or wholesale rollback of *all* independent trust domains remains a separate unresolved threat, not solved by this candidate text.
